# Правила разработки Тыкуэн

## 1. Общие принципы

- Используйте TypeScript и React с функциональными компонентами и хуками.
- Пишите понятный, небольшой и поддерживаемый код.
- Не добавляйте комментарии в исходный код. Неочевидные решения объясняйте в документации или описании Pull Request.
- Не используйте `any` без обоснованной необходимости.
- Проверяйте и валидируйте данные на границах приложения.
- Не храните пароли, токены, ключи и другие секреты в репозитории.
- Не добавляйте зависимости без необходимости.

## 2. Именование файлов и кода

- React-компоненты: `PascalCase.tsx`, например `ListingCard.tsx`.
- Хуки: `useCamelCase.ts`, например `useFavorites.ts`.
- Функции и переменные: `camelCase`.
- Типы и интерфейсы: `PascalCase`.
- Константы верхнего уровня, действительно являющиеся константами: `UPPER_SNAKE_CASE`.
- Каталоги и обычные файлы: `kebab-case`, если формат не диктуется инструментом.
- Тесты: имя тестируемого модуля с суффиксом `.test.ts` или `.test.tsx`.

## 3. Ветки

Используйте короткие имена на английском языке в нижнем регистре, слова разделяйте дефисами:

- `feature/listing-search` — новая функциональность.
- `bugfix/fix-login-validation` — исправление ошибки.
- `hotfix/security-policy` — срочное исправление.
- `docs/update-readme` — документация.
- `refactor/listing-card` — рефакторинг.
- `test/favorites-service` — тесты.
- `chore/update-dependencies` — технические задачи.

Ветка `main` предназначена для стабильного состояния. Рабочие изменения выполняются в отдельных ветках и предлагаются через Pull Request.

## 4. Коммиты

Формат сообщения: `type: краткое описание на английском`.

Рекомендуемые типы:

- `feat` — новая возможность.
- `fix` — исправление ошибки.
- `docs` — документация.
- `style` — форматирование без изменения поведения.
- `refactor` — изменение структуры без изменения поведения.
- `test` — тесты.
- `chore` — обслуживание проекта.

Примеры:

- `feat: add listing search`
- `fix: validate listing price`
- `docs: describe branch naming rules`
- `test: cover favorites service`

Один коммит должен описывать логически цельное изменение. Избегайте сообщений вроде `update`, `fixes` или `changes`.

## 5. Стиль и качество кода

- Соблюдайте единый стиль форматирования через Prettier.
- Используйте ESLint для статического анализа.
- Предпочитайте явные типы и узкие типы вместо неограниченных значений.
- Выносите повторяющуюся логику в переиспользуемые функции или хуки.
- Держите компоненты сфокусированными на одной задаче.
- Обрабатывайте состояния загрузки, ошибки и пустые результаты.
- Не коммитьте временные файлы, сборки, локальные настройки и секреты.

## 6. Проверки перед Pull Request

После настройки соответствующих npm-скриптов запускайте доступные проверки:

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

Если какой-либо скрипт ещё не настроен, отметьте это в описании Pull Request. Не утверждайте, что проверка пройдена, если она не запускалась.

## 7. Code review

1. Создайте Pull Request из рабочей ветки в `main`.
2. Укажите цель изменения, основные решения и способ проверки.
3. Свяжите Pull Request с задачей, если она существует.
4. Проверьте собственный diff и убедитесь, что в него не попали секреты, лишние файлы или отладочный код.
5. Проверяющий оценивает корректность, читаемость, безопасность, тесты и соответствие требованиям.
6. Обсудите замечания и внесите необходимые изменения.
7. Объединяйте изменения после устранения блокирующих замечаний и успешных обязательных проверок.

## 8. Документация

Изменяйте README, архитектурную документацию и записи решений вместе с кодом, если меняются инструкции, структура или существенные технические решения.
